Testabilidade — HU-102: Cancelamento de pedido pelo cliente

Veredito: pronta com ressalvas.

As regras principais de cancelamento estão descritas: quem pode cancelar, status permitidos, tamanho do motivo, status final e respostas esperadas para alguns casos. Porém, há lacunas sobre o acesso por papel e os critérios não cobrem todos os estados já definidos na própria história.

Pontos a esclarecer

#: 1
Trecho (literal): “Só o dono do pedido pode cancelá-lo. Atendente e admin não
  cancelam por esta tela.” (HU-102, linha 10)
Problema: A regra limita explicitamente atendente e admin “por esta tela”, mas
  não define o resultado esperado se esses papéis chamarem a API diretamente.
Pergunta ao PO: Atendente e admin devem ser impedidos também pela API? Se sim,
  qual resposta esperada?
────────────────────────────────────────
#: 2
Trecho (literal): “Com enviado, entregue ou cancelado, o botão ‘Cancelar
  pedido’ não aparece e a API responde 409.” (HU-102, linhas 11–12)
Problema: O critério de aceite cobre somente o status enviado; não confirma o
  comportamento da interface e da API para entregue e cancelado.
Pergunta ao PO: A regra de ocultar o botão e responder 409 se aplica
  igualmente aos três status?
────────────────────────────────────────
#: 3
Trecho (literal): “O motivo é obrigatório: texto livre de 5 a 200 caracteres.”
  (HU-102, linha 13)
Problema: Os critérios cobrem motivo com 4 caracteres e acima de 200, mas não
  especificam o resultado para motivo ausente ou vazio. A API declara motivo
  obrigatório e resposta 400 para motivo ausente ou fora do tamanho (OpenAPI,
  linhas 63–65 e 72).
Pergunta ao PO: Para motivo vazio, a API também responde 400? E espaços contam
  como caracteres válidos?

Observações opcionais

- A história promete e-mail em até 5 minutos para cancelamento, mas o critério explícito de e-mail cobre apenas pedido criado (HU-102, linhas 16–17 e 20–23). O PO pode confirmar se o mesmo prazo vale para pedido pago; a HU-095 processa o estorno, que está fora desta história (linha 15).
- A HU declara que o estorno integral é processado pela HU-095 e está fora do escopo desta história (HU-102, linhas 14–15). O critério “o estorno é solicitado (HU-095)” (linha 23) permite testar a solicitação, mas o contrato OpenAPI não detalha como verificar essa integração.

Riscos já visíveis

- Autorização: a história exige que apenas o dono cancele e exclui atendente e admin pela tela (HU-102, linha 10). A API exige Bearer token (OpenAPI, linhas 8–9 e 76–78), mas não define no contrato o comportamento de autorização por papel. Isso deixa uma pergunta de governança de acesso à API, além da testabilidade.
- Pedido de outro cliente: o critério especifica resposta 404 e pedido inalterado (HU-102, linhas 26–27). Convém validar ambos para evitar exposição ou alteração indevida de pedidos.
